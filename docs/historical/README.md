# RadiaCode firmware — extracted, decompiled, documented

Reverse engineering of the **RadiaCode-102** scintillation dosimeter firmware (unit in hand: serial
`RC-102-008228`, BLE `52:43:06:60:20:24`, hardware `1`, firmware **4.14**). Everything here was produced
by one rerunnable pipeline (`pipeline/run.py`, 17 steps) that talks to the device over **BLE only**
(Nordic UART Service) plus the vendor download site. No JTAG/SWD was used, and no write/erase command
other than the two idempotent session writes described in §2.

Six builds are registered (one directory per model under `firmware/`, each holding one firmware
version): the RadiaCode-102 `hw1-fw4.14` build is the fully analyzed reference, the other five carry
their vendor container plus the decoded/disassembled artifacts (§3.1).

## 2. How the firmware was extracted

The device exposes **no memory-read command** (a complete `0x0000`-`0x0FFF` sweep, with and without a
`u32` argument, answers on 13 ids only - see `analysis/sweep_noarg.json` and
`sweep_witharg.json`). Bulk bytes therefore come from the vendor container, and identity with the unit
in hand is proven by four independent matches:

```
              device (BLE)                     vendor file
   ┌───────────────────────────┐        ┌────────────────────────────┐
   │ 0x0012 FW_IMAGE_GET_INFO  │        │ …/hw1-fw4.14/rc-102z.bin   │
   │  size      = 130148       │ <====> │ len(...)        = 130148   │
   │  date_time = 0x5AE7428A   │ <====> │ header.date_time           │
   │  crc32     = 0x13095ABB   │ <====> │ crc32(whole file)          │
   │ 0x0013 = 19 frames        │ <====> │ 8 Mangle/LZSS blocks       │
   │ 0x0101 = "rc-102.bin",    │ <====> │ name + product in header   │
   │        "RadiaCode RC-102" │        │                            │
   │ VS 0x002 config text 3256 │ <====> │ in-image bytes @0x0802F9F0 │
   └───────────────────────────┘        └────────────────────────────┘
             (verification.json: every "…_matches_device" flag is true)
```

Wire details (from the decompiled parser + the community `radiacode` client, and reproduced by
`pipeline/rcble.py`):

```
host -> device, one logical frame, chopped into 18-byte GATT writes
 +---------------------------------------------------------------+
 | u32 LE length | u16 LE cmd | u8 0x00 | u8 seq | args ...      |
 +---------------------------------------------------------------+
                             |            └ 0x80 + (counter % 32)
                             └ header byte is always 0

device -> host, one notify stream
 +---------------------------------------------------------------+
 | u32 LE length | u16 LE cmd | u8 0x00 | u8 seq | u32 version   |
 |                                        (echo)  | u32 size      |
 |                                                | data[size]    |
 +---------------------------------------------------------------+
   matching: the reply header (4 B) must equal the request header
```

Two writes are unavoidable and both are idempotent: `SET_EXCHANGE` (`0x0007`, sign `01 FF 12 FF`,
the compiled constant `0xFF12FF01` sits at `0x08027DA0` / `0x08028EEC`) opens the session - before it,
most ids stay silent - and `SET_LOCAL_TIME` (`0x0A04`, eight `u8` fields) refreshes the clock. Every
other id used by the pipeline is a read.

The four parameter/record areas read with `0x081C` arrive XOR-obfuscated with a seeded Borland LCG
(`seed = seed * 0x015A4E35 + 1`, byte keystream `(seed >> 16) & 0xFF`, one continuous state: the size
word first, then the payload), which `pipeline/protocol.py` unwraps.

## 3. The pipeline (one entry point, 17 steps)

Every step is a separate process whose paths come from `pipeline/config.py`, which resolves the
active target key against the registry `pipeline/devices.json`. One target = one directory, so runs
never interfere with each other.

```
   python pipeline/run.py                          # every step, for the default target
   python pipeline/run.py --list                   # targets + step table
   python pipeline/run.py --device rc-110/fw4.14   # one build
   python pipeline/run.py --all-devices            # all six, in registry order
   python pipeline/run.py --only 1,4,5             # selected steps
   python pipeline/run.py --from 7                 # resume at step 7
   python pipeline/run.py 2 --sweep                # step 2 plus the long id sweep
   $env:RC_TARGET='rc-410/fw4.16'; python pipeline/step5_disassemble.py   # steps run alone too
```

| # | file | needs | what it does | writes (inside the target dir) |
| --- | --- | --- | --- | --- |
| 1 | `step1_validate.py` | offline | self-test the container primitives against the `PhytonUtils` reference vectors | stdout |
| 2 | `step2_probe.py` | BLE | read-only capture: identity, 15 virtual strings, register index space, 4 parameter areas; `--sweep` adds both id sweeps | `analysis/capture.json`, `analysis/sweep_{noarg,witharg}.json` |
| 3 | `step3_fetch.py` | network | download `RadiaCode.apk` + `RadiaCode.exe`, unpack the containers into their target dirs, match `size / date_time / crc32` | `<container>.bin`, `official/{apk,exe}.bin`, `analysis/container_check.json` |
| 4 | `step4_decode.py` | offline | header parse, per-block Mangle decrypt + CRC + LZSS -> flat image | `flash.bin`, `blocks.json` |
| 5 | `step5_disassemble.py` | offline | capstone Thumb-2 linear sweep, data-item classification, string + vector tables | `listing.s`, `analysis/{strings,vectors,functions,stats}.json` |
| 6 | `step6_decompile.py` | Ghidra | headless `analyzeHeadless` + `pipeline/scripts/DumpC.java` post-script | `decompiled.c`, `ghidra_proj/` |
| 7 | `step7_index_c.py` | offline | function -> C line-range index | `index.json` |
| 8 | `step8_xrefs.py` | offline | literal-pool xrefs: which function loads which string / callee | `analysis/xrefs.json` |
| 9 | `step9_callgraph.py` | offline | BFS reachability from every vector handler | `analysis/callgraph.json` |
| 10 | `step10_tables.py` | offline | static `{id, getter/handler}` runs (the numbered 91-entry table, the 44-entry registry) | `analysis/tables.json` |
| 11 | `step11_verify.py` | BLE | byte-for-byte device vs image verification, plus the registry cross-check | `analysis/verification.json` |
| 12 | `step12_report.py` | offline | statistics report + this build's identity/checksum manifest | `analysis/summary.md`, `manifest.json` |
| 13 | `step13_roundtrip.py` | offline | **L1** container re-encode from the model, byte diff vs the vendor file; LZSS encoder equivalence | `analysis/roundtrip.json` |
| 14 | `step14_crosscheck.py` | offline | **L2** capstone vs Ghidra/SLEIGH instruction agreement, graded in four tiers | `analysis/crosscheck.json` |
| 15 | `step15_differential.py` | offline | **L4** Unicorn execution of the original code vs the Python models, plus pure-model vectors | `analysis/differential.json` |
| 16 | `step16_formal.py` | offline | **L5** Z3 proofs over the side-effect-free parts of the model | `analysis/formal.json` |
| 17 | `step17_confidence.py` | offline | roll every evidence file up into the five confidence categories | `analysis/confidence.json`, `analysis/confidence.md` |

Steps 2 and 11 self-skip (exit 0) for targets whose `ble_address` is `null`; steps 7, 10 and 12
tolerate a missing `decompiled.c`, so a target stays coherent when only steps 1-5 have run. A target that
*does* name a `ble_address` but is powered off fails exactly those two steps
(`BleakDeviceNotFoundError`, `15/17` for that build) - the artifacts of the last live capture stay on
disk, so the offline layers are unaffected.
Steps 13-17 are the verification layers and are offline as well: 14 needs `ghidra_listing.json`
(written by the `DumpListing.java` post-script of step 6) and skips itself when it is absent; 15 runs
only the models whose 16-byte signature still matches the image of the target being checked.

Helper modules (importable, no side effects): `pipeline/config.py` (registry + path resolution),
`pipeline/protocol.py` (ids, framing, record decoders), `pipeline/rcble.py` (bleak transport +
framing), `pipeline/rcsession.py` (retrying session), `pipeline/rcfmt.py` (Phyton container both ways:
Mangle Feistel, CRC-32/MPEG-2, LZSS decode *and* encode, `reencode_file`), `pipeline/emulate.py`
(Unicorn harness: region maps, `run_function`, write trace), `pipeline/models.py` (hand transcriptions
of the routines under test + their 16-byte signatures). One-off inspectors live in `pipeline/tools/`
(`lookup.py`, `read_vsfrs.py`, `probe.py`, `inspect_image.py`, `inspect_blocks.py`,
`inspect_vectors.py`, `debug_*.py`, `blescan.py`, `ifaces.py`, `fetch_apk.py`, `analyze_official.py`);
they read the same registry, so `RC_TARGET=…` selects the build they look at.

Requirements: Python 3.13 + `bleak` (BLE), `capstone` (disassembly), `unicorn` (step 15), `z3-solver`
(step 16), and an unpacked `ghidra_12.2_PUBLIC/` + `jdk-25.0.5+8/` next to the repo root for step 6
(and therefore for the SLEIGH side of step 14). Steps 1, 4, 5, 7-10, 12-17 are pure offline
recomputation from committed artifacts, so the whole analysis is reproducible without the hardware.

### 3.2 Adding a device or a firmware version

1. Append one block to `pipeline/devices.json` - `key`, `model`, `device`, `hw`, `fw`, `boot`,
   `analyzed` (drives the "analyzed" column of each `summary.md`), `serial`, `ble_address` (`null` when
   no unit is in hand), `dir`, `containers`, `primary_container`, `mcu` (family, processor id, base,
   vector table, initial SP, reset), `expected` (`size / chunk / buffer_size / date_time / crc32 /
   frames / blocks`) and `landmarks` (the addresses the reports quote; an empty block prints `n/a`).
   No step file needs editing.
2. `python pipeline/run.py --device <key>` - step 3 unpacks the container into that directory from the
   vendor APK, then 4-17 build the rest. With a unit attached, fill in `ble_address` and run steps 2
   and 11 to get the on-device evidence; steps 13-17 need nothing but the artifacts on disk.
3. A new firmware version of an existing model is another block with a different `dir`
   (`firmware/rc-102/hw1-fw4.15`), so old and new builds sit side by side and every diagram keeps its
   exact byte offsets.

The two installers in `official/` (`apk.bin`, `exe.bin`, ~55 MB together) are gitignored and refetched
by `--only 3`; the containers themselves are committed inside the target directories.

## 4. Confidence in the decompilation

Measured, in five categories that are deliberately **not** merged into one number: each answers a
different question and each comes from a different kind of evidence. Steps 13-17 produce them without
the device; `analysis/confidence.json` is the machine-readable form, `analysis/confidence.md` the
readable one. Values below are `rc-102/hw1-fw4.14` as produced by
`python pipeline/run.py --only 13,14,15,16,17`.

| category | what it asks | measured | evidence |
| --- | --- | --- | --- |
| **byte_matched** | does the model write the vendor file back? | `130148/130148` container bytes, key blocks `8/8`, data blocks `8/8`, header + CRC field equal, key-block CRC pair equal `8/8`, whole-file CRC equal to the device's `0x0012` reply | step 13 (`rcfmt.reencode_file`, carried pass) |
| **formally_verified** | does the property hold for *every* input? | `10/10` goals proved by Z3: Mangle one round + the 48-round chain are permutations, CRC register and word-step forms agree, Borland LCG full period (Hull-Dobell), MS-DOS date pack/unpack, LZSS token + window-slot layout, `align_size` is the least multiple of 8 | step 16 |
| **tested** | does the original machine code agree with the model? | `8/8` function cases (122 instructions executed; the returned word **and** every byte the routine wrote must be equal, ABI stack slots excluded), `189/189` model vectors (`183` synthetic + `6` anchored on the unit's own `0x081C` replies), `8/8` block decompressed-length identities, and on the disassembly side `39260` lines compared with `0.9999` agreement (`4` semantic differences left) | steps 15, 13, 14 |
| **preserved_unchanged** | what is carried verbatim at its original address? | `248320/248320` image bytes covered, `66745` decoded instructions, `1895` C blocks, `1027` data/ascii items, `3888` key-block tail bytes | steps 5, 6, 13 |
| **unresolved** | what is still open? | `4` named items: the per-block CRC-pair definition, LZSS bit-exactness of the pipeline's own encoder (`4649/31831` tokens, `125890` vs `125815` bits), `4` non-identical disassembly lines, `28676`/`1483` lines only one decoder reaches | step 17 |

How each layer works, and what its limits are:

* **L1 container byte-exactness** (step 13). The decoder is inverted: header fields, the two XOR
  masks, the Mangle keys and the payload stream are written again and compared byte by byte -
  `130148/130148` bytes, `identical: true`, and every per-block key/data/size match is `8/8`. A second
  pass also pushes the payload through `rcfmt.lzss_compress`; there each stream still *decodes* to the
  identical plaintext (`8/8`) but is not bit-identical: the first divergence lands after 2088 bits /
  497 tokens of the first block, overall `4649/31831` tokens agree and the totals are `125890` vendor vs
  `125815` own bits - a tie-break/search-order difference inside the vendor's hash chain. So the
  compressor is credited with "decodes identically, `8/8`" rather than "bit-identical".
* **L2 cross-decoder agreement** (step 14). `listing.s` is capstone's; `analysis/ghidra_listing.json`
  is Ghidra's own SLEIGH decode of the same bytes. Text is never compared raw: the tiers are
  `identical`, `format_only` (same mnemonic, same numeric operands), `pc_relative` (immediate vs
  resolved literal, PC = word-aligned instruction address + 4) and `semantic`. The 4 semantic lines
  are real decoding differences at code/data boundaries and are listed in the JSON.
* **L4 differential execution** (step 15). Unicorn runs the original Thumb code with the image mapped
  at `0x08000000`; the model is a hand transcription of the same `decompiled.c` block. Both start from
  the same preset, and the comparison covers the returned word plus every byte-level memory effect.
  A model is only run on a target whose 16-byte signature at that address still matches the build it
  was transcribed from, which is why `rc-101`, `rc-110` and `rc-410` report `0/0` cases.
* **L5 formal checks** (step 16). Only side-effect-free routines are eligible. `proved` needs the
  negation to be unsatisfiable; `unknown` (timeout) and `counterexample` (with witness) are recorded
  separately and never counted as passes.
* **Device-anchored vectors** (step 15, `borland_lcg_device`). The `0x081C` replies stored in
  `analysis/capture.json` are replayed through the model: the length word must equal the number of bytes
  received, the payload must round-trip, and the 8-bit keystream must leave more `0x00`/`0xFF` padding than
  the 7-bit alternative - which pins the keystream on the unit's own bytes rather than on a self-test.
  Those 6 vectors only exist for a build that has a capture, and the rest of the total scales with the
  container's block count (`mangle_blocks` runs twice per block, `lzss_decode` once): `189` for
  `rc-102` (8 blocks + capture), `183` for the other 8-block builds, `186` for the 9-block `rc-110`,
  `189` again for the 10-block `rc-410`.

The qualitative reading, per artifact:

| artifact | confidence | why |
| --- | --- | --- |
| `flash.bin` (bytes) | **certain** | every block's own CRC verified during decode (step 4), image length + `date_time` + CRC equal the device's `0x0012`, and the 3256-B config text matches the live VS `0x002` byte-for-byte |
| vector table / entry points | **certain** | read directly as words at `0x08010000`; `InitialSP`/`Reset` are consistent with the observed code ranges |

| wire framing + record decoders | **certain** | decoded twice independently: from the decompiled parser and from live replies of the same unit; both agree on every field |
| `[DeviceParams]` / `[DataStructure]` semantics | **high** | the config blob is the device's own answer (VS `0x002`) and is compiled into the image at `0x0802F9F0` |

| callgraph coverage | **medium** | 99 of 1867 functions are reachable from a vector handler; the remaining 1768 are entered through the 8 static dispatch tables and the numbered `{id, getter, setter}` table, which step 10 recovers 85/85 of |
| MCU part number | **low/medium** | family is certain (STM32L4-class Cortex-M4F); the exact orderable part is inferred from the vector names (`LPUART1`, `LPTIM1-4`, `QUADSPI`, `DMA2`, `AES`) |

## 5. Hardware

### 5.1 MCU and on-chip peripherals

The image is a self-contained Cortex-M4 program: vectors at `0x08010000`, `InitialSP = 0x20000800`,
`Reset = 0x0803BA71`, the software-reset constant pair `0x05FA0004` (`SCB->AIRCR`, VECTKEY | SYSRESETREQ)
in literal pools at `0x0801E330`, `0x08022724`, `0x08027DC0`, and a hardware-AES IRQ. Nine exception
stubs (`0x080363FD`-`0x0803640D`) and exactly nine IRQs have their own code; every other vector points at
`0x0803C4D9`, a 4-byte self-loop.

```
  IRQ  handler        what it services (from the code + the vector name)
  ---  ------------   ---------------------------------------------------------
    7  0x0803640F     EXTI1  - button / radio interrupt line
    8  0x08036423     EXTI2  - second external line
    9  0x0803654B     EXTI3
   10  0x08036437     EXTI4
   11  0x08036455     DMA1_CH0  - BLE module + ADC transfers
   12  0x08036475     DMA1_CH1  -> posts event FUN_080191F0
   18  0x080364A1     ADC1_2    - battery / analog sampling
   23  0x080364BF     USART1    - BLE module link
   40  0x080364F9     DMA2_CH0
   50  0x0803651B     AES       - container CRC/crypto helpers
   54  0x0803651F     TIM12
   65  0x08036523     LPUART2
   66  0x0803653B     LPTIM3    - frame tick / wake
   67  0x0803655B     LPTIM4
  rest 0x0803C4D9     self-loop (unused)
```

Each real ISR is a 3-6 instruction trampoline: read a peripheral status word, OR a bit into a shadow
status (`0x20`, `0x40`, `0x80`, ...), post an event. The numbered trampolines at `0x0803C4B6`+ load the id
(`movs r1, #n`) and tail-jump into the shared entry at `0x0803C4B2`. That is the whole interrupt model:
**tiny ISRs + one event pump** (§9).

### 5.3 Battery metrics

There is no dedicated fuel gauge: the level is an ADC ratio plus a charger flag.

```
 CHN_ChargeLevel    id 9, Sensor=MCU_ADC, Unit=%, DType=4, RType=1, Expr=1 P1=0.01  ->  % = raw/100
```

Observed live: the ADC sample floats inside VS `0x100` sit at `4.947917` / `4.875` / `4.770833` V, i.e. a
1-cell LiPo near full charge, and `VSFR_CHARGER_STATE` reports `1`. `BattChargeMonitor=0` plus
`DBLag_ms=180000` explain why the charge/temperature VSFRs answer the bare zero word at idle: the
`GRP_RareData` group that carries them is refreshed on the 3-minute cycle, not per frame.

## 7. Boot-up sequence

```
 reset (hardware) ──► 0x08000000 vendor bootloader
        │
        │  validates the application image (whole-image CRC-32/MPEG-2 + per-block CRCs)
        │  CRC mismatch  -> stays in the bootloader, waits for FW_IMAGE_WRITE
        │  CRC ok        -> jumps to the application vector table
        ▼

        │  1. load SP from 0x08010000 (0x20000800)

        ▼

        │  driver-table dispatcher: for each registered driver, call its poll routine
        ▼
 +----------------------------------------+     +-----------------------------------+
 | event pump @ 0x0803C458-0x0803C4D9     | <-- | ISRs (9 real ones) post bits into |
 | drains queues, runs deferred handlers  |     | a shadow status word              |
 +----------------------------------------+     +-----------------------------------+
        │
        │  peripheral bring-up, in the order the strings appear:
        │    "BLE: Hardware initialization" -> "BLE: Start"     (0x08022EE0-0x08022F34)

```

appears 66 times as a literal: it is both the unused-vector target and the idle spin.

### 8.1 The real-time record stream (VS `0x100`)

Two alternating record sizes, verified by autocorrelation of a captured 1010-byte buffer: the frame
counter byte increments once per record and the anchor spacing is exactly `45, 21, 45, 21, ...`, so one
frame = 45 + 21 = **66 bytes**, i.e. 15 frames + a 65-byte tail in that sample.

```
 one 66-byte frame =  A-record (45 B)  +  B-record (21 B)
 +--------------------------------------------------------------------------------+

 A-record, byte offsets
   0  u8  seq            0x22, +1 per record, +2 per frame
   1  u8  groupId        0x01 = GRP_RawData
   2  u8  channelId      0x02 = CHN_Count
   3  u8  tag            0x2d
   4  u8[3] tick         24-bit LE tick, e.g. 0xE6A994
   7  u8  0x02 | 8 u8 0x00
   9  u32 9600           the UART baud constant
  13  u32 475    | f32 4.947917 | f32 7.438e-06 | u32 stamp (33 01 00 b0)   <- 16 B
  29  u32 468    | f32 4.875    | f32 8.399e-06 | u32 stamp (3a 01 00 b0)   <- 16 B
      header 13 + 2 x 16 = 45

 B-record, byte offsets
   0  u8  seq            0x23 (A + 1)
   1  u8  groupId        0x00 = GRP_RealTimeData
   2  u8  channelId      0x03 = CHN_CountRate
   3  u8  tag            0x40
   4  u8[3] tick         0xE6A9F3, ~90 after the A-record's tick
   7  u32 28403139       window/uptime word, grows by ~250-350 per frame
  11  f32 0.0595957      the sample value
  15  u8  flags          0x8f / 0x84 / 0x78 between frames
  16  u8[5] tail         constant 11 10 27 40 b0
```

Field confidence: **certain** = the 45/21 split and the offsets (the frame-counter anchors sit exactly
45, 21, 45, 21 ... bytes apart in a 1010-byte capture, and a second capture of 1058 bytes shows the same
stride); **high** = `groupId`/`channelId` match the `[DataStructure]` ids (group 1 `GRP_RawData` carries
`CHN_Count`, group 0 `GRP_RealTimeData` carries `CHN_CountRate`), and the `0.0595957` float of the
B-record is the same quantity the `0x8021` VSFR reports, so the stream and the single-value reads are two
views of one sample set; **inferred** = the `9600` constant (UART baud), the 24-bit `tick` (monotone, ~90
ticks A to B, consistent with `FrameTimeStep_us = 10000`) and the trailing stamps.

## 10. Firmware update flow

Three layers, only one of which is the "firmware":

| layer | content | replaced by an update? |
| --- | --- | --- |
| vendor bootloader | `0x08000000`-`0x0800FFFF` (65536 B) | **no** - no block in any container starts below `0x08010000`, so the programmer itself survives |
| application image | `0x08010000`-`0x0803CA00` = `firmware/rc-102/hw1-fw4.14/flash.bin` | **yes**, wholesale: a complete program with the config text compiled in |
| parameter areas | the two `0x081C` records (72 B + 448 B), XOR-obfuscated, seeded | **no** - separate, per-unit, so calibration and serial survive |

```
  app (holds assets/HardSoft/rc-102z.bin locally, 130148 B - no network needed)
   │
   │ 1. SET_EXCHANGE 0x0007  sign 01 FF 12 FF ─────────► session open
   │ 2. FW_IMAGE_GET_INFO 0x0012 ─────────────────────► {size, buffer_size, date_time, crc32}
   │        │
   │        ├─ signature match + CRC match      -> nothing to do
   │        └─ signature match + CRC mismatch    -> "…CRC32 mismatch, resetting" -> transfer
   │ 3. FW_IMAGE_UPDATE ─────────────────────────────► staging session, chunk size = buffer_size
   │ 4. FW_IMAGE_WRITE x N  "FW Image: Writing %d bytes at offset %d"
   │        │        130148 / 4096 ≈ 32 chunks; NAK -> "FW_IMAGE_WRITE returned error #%d"
   │        │        (the # is one of the FLASH_* codes: PROG, NOT_BLANK, WR_PROT, RDP_ERROR,
   │        │         INVALID_CRC, INVALID_SIGN, INVALID_TARGET, INV_ADDR, REQUIRED, VERIFY, STATE)
   │ 5. device recomputes whole-image CRC-32/MPEG-2 + per-block CRCs
   │        mismatch -> "CRC Error: 0x%08X != 0x%08X"  @0x08027294, old image stays active
   │ 6. reboot: SCB->AIRCR = 0x05FA0004, BLE drops, app reconnects
   │        no reconnect -> "RECONNECTION_TIMED_OUT_DURING_UPDATE"
   ▼
 bootloader re-validates, jumps to 0x08010001
```

Progress is surfaced per chunk through `FWProgressUpdater` / `EVT_FW_WRITE` (SDK names from
`classes.dex`, package `ru.almacode.vk.corelib`).

### 10.1 Fresh flash (blank part)

```

   │
   ├─ 1. SET_EXCHANGE            id 0x0007 must answer, otherwise the link/ framing is wrong
   ├─ 2. FW_IMAGE_GET_INFO       a blank device answers size = 0 / crc = 0xFFFFFFFF
   ├─ 3. FW_IMAGE_UPDATE         opens the staging session (buffer_size from step 2)
   ├─ 4. FW_IMAGE_WRITE x N      offset-ordered chunks; each chunk carries its own CRC in the container
   ├─ 5. verify                  device-side CRC-32/MPEG-2 must equal 0x13095ABB for this build
   └─ 6. system reset            new vectors take effect immediately (VTOR = 0x08010000)
```

### 10.2 Anti-brick properties

| control | evidence |
| --- | --- |
| every frame is length-prefixed and validated on 4 independent fields before anything executes | the five `Error: S%d …` strings @ `0x08037267`-`0x08037354` |
| a session must be opened before state-changing ids take effect, so a stray packet cannot half-program the device | `SET_EXCHANGE` gating (observed), constant `0xFF12FF01` |
| whole-image CRC **and** per-block CRCs must match before activation | `CRC Error: 0x%08X != 0x%08X`, poly table at `0x0801F424`/`0x0802ACD8`/`0x0802D748`, `FLASH_INVALID_CRC` |
| the write path reports the flash controller's own error bits | `FLASH_PROG`, `FLASH_NOT_BLANK`, `FLASH_WR_PROT`, `FLASH_RDP_ERROR`, `FLASH_VERIFY` |
| the bootloader is outside every container, so it is never overwritten | all 8 blocks start at `0x08010000` or higher |
| a failed/timed-out transfer leaves the previous image active | activation happens only after the CRC check; `RECONNECTION_TIMED_OUT_DURING_UPDATE` |
| calibration/serial records are separate from the code image | the two `0x081C` areas keep their own seed + XOR stream |
| only 13 ids accept anything at all | `analysis/sweep_noarg.json`, `analysis/sweep_witharg.json` |

## 11. What we can do / what we are locked out of

Legend: **R** = read-only command, **W** = write command, **(inf)** = interpretation of structure.

| capability | how | status |
| --- | --- | --- |
| identify the unit (serial, BLE name, product, build stamp) | `0x000B`, `0x000A`, `0x0101` | R - works |
| get the exact firmware identity (size / date_time / crc32 / chunk size) | `0x0012` | R - works |
| get the frame count of the staged image | `0x0013` | R - works |
| read the whole vendor configuration + channel model as text (3256 B) | `0x0826` VS `0x002` | R - works, byte-identical to the in-image blob |
| read the energy calibration polynomial | `0x0826` VS `0x202` | R - works |
| read a live spectrum header + accumulated counts | `0x0826` VS `0x200`, `0x205`, `0x220` | R - works |
| read the real-time measurement stream | `0x0826` VS `0x100` | R - works, grammar in §8.1 |
| read the event log ring (BLE connect/disconnect, lost messages) | `0x0826` VS `0x00F` | R - works |
| read per-unit parameter/calibration areas | `0x081C` areas 0 and 1 | R - works, XOR-unwrapped |
| read individual sensors (dose rate, dose, counts, window) | `0x0824` + VSFR address | R - 20 of 67 entries answer at idle; the rare-data group needs the 3-min cycle |
| read the MCU identity / version words | `0x0824` `0xFFFF0000`+ | R - works |
| set the wall clock | `0x0A04` | W - idempotent, used by the pipeline |
| open the protocol session | `0x0007` | W - idempotent sign |
| **full 1024-channel spectrum array** | - | **locked out**: the array is not exposed by any answering id; only the 22-byte header/calib records come back |
| **raw memory read** (no `READ_MEM` id exists) | - | **locked out**: proven by two complete `0x0000`-`0x0FFF` sweeps |
| **bulk image bytes from the device** | - | **locked out** by design; the bytes come from the vendor container instead, identity proven by the CRC triple |
| **write calibration / parameter areas** | `0x0825`, `0x0827`, `0x082B` exist in the SDK name list | **not exercised** - the pipeline is read-only by policy; the SDK names them but they were never issued here |
| **raw SWD/JTAG dump** | - | locked out: not used (BLE-only workflow) |
| **enumerate the 91-entry item table through the index form** | `0x0824` args `0x00`-`0x5A` | **no data**: all 91 answer `00000000` on this build - the table is recovered statically instead (step 10) |
| batch VSFR reads | `0x082A` | partial: answers for the plain `u32` address form only |
| name resolution for the 1867 functions | - | **open**: Ghidra auto-names only (`FUN_…`); meaning comes from strings, tables and live reads |
| confirm the exact STM32L4 orderable part | vector names | **inferred only** (family is certain) |

Two structural observations fall out of that matrix: the protocol is a *closed* surface (13 ids, all
validated, no raw memory access), and every bulk quantity on the device is reachable through exactly one
channel - the `{u32 version, u32 size, data}` envelope of `RD_VIRT_STRING`. That is why the pipeline
reads the same envelope 15 times with different ids instead of trying to walk memory.

## 13. Known limits and open questions

* The listing is a linear sweep, so short data runs between functions decode as plausible instructions;
  trust mnemonics inside known ranges, expect `.word` / `ascii` / `.fill` lines for pools.
* Two functions remain stubs (`0x08016CC6`, `0x0802ABF8`): data-table slots whose bodies exist only as
  disassembly.
* `0x08036C10`'s 44-entry table is *not* the BLE command table (its ids `0x400`-`0x40A`, `0x800`-`0x80A`,
  `0xC01`-`0xC18` do not match any id that answers on the wire); it is an internal object/property
  registry, while the real per-item dispatcher is the switch at `0x080275C4`.
* `date_time` (`0x5AE7428A`) is the container header stamp, in **MS-DOS packed date/time** form - the
  high half is `(year-1980)<<9 | month<<5 | day`, the low half `hour<<11 | minute<<5 | (second/2)`, so
  it decodes to 2025-07-07 08:20:20 (`rcfmt._decode_datetime`); it is *not* a Unix epoch. The in-image string
  `Jul 7 2025 11:19:22` is the compiled `__DATE__ __TIME__` of the same build. Both are correct, they are
  two different clocks (packaging vs compilation).
* The 76-byte `0x0F0` / `0x203` record is decomposed structurally (magic `0x19601217`, `u16`/`u16` group
  headers, 13 plausible IEEE-754 floats) but 5 of its words have no confirmed meaning yet; the three
  floats that do match VS `0x202`'s calibration triple.
* 1768 of 1867 functions are not reachable from a vector handler; they are entered through the 8 static
  tables and the numbered item table. Per-handler attribution is therefore table-driven, not stack-based.
* Four items stay open after the verification layers (§4, and machine-readable in
  `analysis/confidence.json -> unresolved`): the definition of the per-block key-block CRC pair beyond its
  two words being equal; bit-exactness of the pipeline's own LZSS encoder against the vendor stream
  (decoding is identical, token choice diverges); `4` disassembly lines where capstone and SLEIGH still
  disagree; and the lines only one of the two decoders reaches. Each is a bounded question, not a gap in
  the bytes themselves - `flash.bin` is verified block by block and end to end.

## 14. Glossary

| term | meaning |
| --- | --- |
| `Phyton\0\0` container | the vendor's `.bin` firmware file format: 52-byte header + N Mangle-encrypted, LZSS-compressed blocks |
| Mangle | the 48-round Feistel cipher over 8-byte blocks used per block, 4 round keys, round function `B' = rnd + key + ((B>>8)^(B<<6)) + B + A` |
| Borland LCG XOR | `seed = seed*0x015A4E35 + 1`, keystream `(seed >> 16) & 0xFF`, used by `RD_FLASH_AREA` |
| VSFR | virtual special-function register: a software-decoded named value with `{addr, size, type, flags, min, max}`, not a memory-mapped one |
| VS | "virtual string": a numbered blob served by `RD_VIRT_STRING` (`0x0826`) |
| NUS | Nordic UART Service, the BLE GATT service pair used for the wire (`e63215e5-…`, write `…e6`, notify `…e7`) |
| MCA | multi-channel analyzer: the pulse-height histogram (1024 channels) behind the spectrum |
| `S%d` | slot/sequence index appearing in the five framing-error strings |
